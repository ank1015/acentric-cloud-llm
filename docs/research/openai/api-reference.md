## 1. `POST /v1/responses` request body

Base URL `https://api.openai.com/v1`, Bearer auth. Response: `200` `application/json` (`Response`) or `text/event-stream` when `stream:true`; `400/404/429/503` use `ErrorResponse` (see section 9). All body fields are optional in the schema (`required: []`), including `model`, because a `prompt` template can supply them.

Legend for the "Status" column: GA = in the main spec and reference; NEW = added in the last ~9 months; DEPR = marked deprecated; BETA = only in the `?beta=true` flavour.

### 1.3 `include` values (`IncludeEnum`, 8)

`file_search_call.results`, `web_search_call.results` (in enum, missing from the reference's description list), `web_search_call.action.sources`, `message.input_image.image_url`, `computer_call_output.output.image_url`, `code_interpreter_call.outputs`, `reasoning.encrypted_content`, `message.output_text.logprobs`.

`reasoning.encrypted_content` is now legacy: reasoning items in `output` carry `encrypted_content` by default (per SDK jsdoc and reasoning guide); the value is still accepted. When streaming, take the item from `response.output_item.done`, not `.added`.

## 2. INPUT item union (`input: string | InputItem[]`)

`InputItem` = `EasyInputMessage | Item | CompactionTrigger | ItemReference | Program | ProgramOutput`; `Item` has 28 members. Total 33 variants in the reference. Output items are replayable as input (the `Item` union reuses the output schemas for `message`, `reasoning`, `function_call`, all `*_call` items). Required fields are marked `*`. `id` and `status` on input items are generally optional and "populated when returned via API".

### 2.1 Messages

| Item                                     | Fields                                                                                                                                                  | Notes                                                                                                      |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `EasyInputMessage`                       | `role*`: `user\|assistant\|system\|developer`; `content*`: string \| `InputContent[]`; `phase?`: `commentary\|final_answer\|null`; `type?`: `"message"` | Easy form (type optional, string content).                                                                 |
| `Message` (`InputMessage`)               | `type?` `"message"`, `role*`: `user\|system\|developer`, `content*`: `InputContent[]`, `status?`                                                        | Strict form. No assistant role here.                                                                       |
| `message` (assistant, = `OutputMessage`) | `id*, type* "message", role* "assistant", content*: (output_text\|refusal)[], status* (in_progress\|completed\|incomplete), phase?`                     | Replay of model messages. `id` and `status` are required in this form, which is why SDK helper keeps them. |

`phase`: Feb 2026 feature. For models from `gpt-5.3-codex` on, "preserve and resend phase on all assistant messages, dropping it can degrade performance" (spec text). Docs: GPT-5.5 can treat an intermediate update as the final answer if `phase` is dropped.

### 2.2 Input content parts (`InputContent`, 3 variants)

There is NO audio input part in the Responses input union. `EasyInputMessage.content`'s description still says "text, image, or audio", the SDK exports an unused `ResponseInputAudio` type, and the spec's `InputAudio` is only referenced by Evals. Treat audio input as unsupported on Responses.

| Part          | Fields                                                                                                                                    | Limits / notes                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `input_text`  | `type*`, `text*`, `prompt_cache_breakpoint?: {mode:"explicit"}`                                                                           | text <= 10 MiB (10485760).                                                                                                                                                                                                                                                                                                                                                                                                     |
| `input_image` | `type*`, `detail?: low\|high\|auto\|original` (default `auto`), `image_url?` (URL or `data:` URL), `file_id?`, `prompt_cache_breakpoint?` | `image_url` <= 20 MiB (20971520). In the response-side schema `detail` is required, in the Param schema optional.                                                                                                                                                                                                                                                                                                              |
| `input_file`  | `type*`, `file_id?`, `file_url?`, `file_data?`, `filename?`, `detail?: auto\|low\|high`, `prompt_cache_breakpoint?`                       | `file_data` <= 70 MiB (73400320). Docs examples use a data URL (`data:application/pdf;base64,...`) while the Param schema description says "base64-encoded data". Use the data URL form. File guide: 50 MB per file and per request combined; Responses accepts PDFs plus docx/pptx/txt/code (text only) and spreadsheets; `file_url` is Responses-only. `detail` for GPT-5.6+: `auto` = high-quality rendering (more tokens). |

`prompt_cache_breakpoint` is accepted on all three part types, including parts inside `function_call_output.output[]`. It is NOT accepted on `additional_tools` items and cannot be placed in top-level `instructions`.

### 2.5 Replay rules the official SDK applies (`toResponseInputItems`)

Source: `openai-node/src/lib/responses/ResponseInputItems.ts` and its tests.

1. Strip the output-only field `created_by` from every item (including inside `shell_call_output.output[]`).
2. Drop `computer_call_output` items with `status:"failed"`.
3. Drop `custom_tool_call_output` items whose `status != "completed"`, and remove `status` from the ones kept.
4. Drop `additional_tools` items whose `role != "developer"` (the output schema permits other roles, e.g. `assistant`).
5. Strip SDK-only fields (`parsed`, `parsed_arguments`).
6. Everything else is passed through as is. Unknown item types make the helper throw, a hint that new item types appear regularly.

Docs rule: for stateless use "preserve every item in the response's `output` array" (reasoning, `phase`, compaction, program, etc.). After a compaction item you may drop items before the latest compaction item.

## 6. Roles: `system` vs `developer`, and mid-conversation messages

- Roles accepted in `input` messages: `user`, `assistant`, `system`, `developer`. `InputMessage` (strict) takes `user|system|developer`; assistant text is expressed via `EasyInputMessage` or the output-message form.
- The spec text for both message forms: "Instructions given with the `developer` or `system` role take precedence over instructions given with the `user` role". The guides (text, prompt-engineering) only talk about `developer` and never mention `system`; the migration guide still shows `system`. The Chat Completions spec says "With o1 models and newer, `developer` messages replace the previous `system` messages". I found no documented behavioural difference between the two on Responses; treat `system` as a legacy alias with equal authority. Whether the server internally rewrites one to the other: UNVERIFIED.
- `instructions` is functionally a developer message at the head of the context, applies to this request only (not inherited through `previous_response_id`), and cannot carry an explicit cache breakpoint. If you want a breakpoint on it, you must send it as a `developer` message with an `input_text` part.
- Mid-conversation developer/system messages: the schema is a flat list, so a `developer`/`system` message can appear at any position and nothing in the spec restricts it. The prompt-caching guide acknowledges the case ("developer messages after the initial consecutive block of developer messages are not automatic implicit-mode cache boundaries; add an explicit breakpoint"). Two more mid-conversation developer-class items exist: `additional_tools` (role fixed to `developer`) and `configuration_update`. I did not find any doc on mid-conversation `system` specifically.
- `assistant` messages in `input` are "presumed to have been generated by the model in previous interactions".

| `multi_agent`                                               | **Refuse/unsupported** (beta, other path flavour, needs a header)                                                                                                                                                                                                                                                         |                                                                                                                                                                            |

Candidates for the "OpenAI profile" rather than the "base Responses format" (Fireworks, xAI etc. may not implement them; verify in their research): `access_programs`, `moderation`, `prompt_cache_options`, `service_tier` values, `reasoning.context/mode`, `context_management`, `max_tool_calls`, `prompt`, programmatic tool calling, async tools, `namespace`, `tool_search`, `additional_tools`, `configuration_update`, `compaction*`, `phase` (possibly).

### 7.4 Stop reasons

OpenAI has NO stop-reason field. It must be derived:

| Our reason       | Derivation                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tool_use`       | `status:"completed"` and at least one client-owned call item with no matching output item with the same `call_id` in the same `output` (`function_call`, `custom_tool_call`, `computer_call`, `local_shell_call`, local `shell_call`, `apply_patch_call`, client `tool_search_call`, `mcp_approval_request`). A message may be present too (async tools and commentary phases do this). |
| `stop`           | `completed`, no pending client calls, final message present.                                                                                                                                                                                                                                                                                                                            |
| `length`         | `status:"incomplete"` and `incomplete_details.reason == "max_output_tokens"` (may have no visible output, since reasoning consumed the budget). `max_messages` is unexplained, likely length-like.                                                                                                                                                                                      |
| `refusal`        | A `refusal` content part in a message (status is still `completed`). Also `error.code` `bio_policy`/`misalignment_policy_violation` when `status:"failed"` could reasonably map here or to `content_filter`.                                                                                                                                                                            |
| `content_filter` | `incomplete_details.reason == "content_filter"`; also input/output moderation blocks (`moderation.policy.*.mode: "block"`) and image policy errors (`image_content_policy_violation`, `invalid_prompt`) when surfaced as 200 with `status:"failed"`.                                                                                                                                    |
| `pause_turn`     | No native field. Closest: `completed`, no final message and no pending client calls (e.g. hosted tool items or a `program` without `program_output`), where docs say "continue from that response" by replaying output. Heuristic, caller must re-send. Otherwise N/A for HTTP (`steered` is WebSocket only).                                                                           |
| error            | `status:"failed"` with `error{code,message}` -> structured error. HTTP errors use the `{error:{type,message,param,code}}` envelope.                                                                                                                                                                                                                                                     |

## 8. What does not fit our design

1. **Hosted and exotic tools cannot be expressed.** The shared tool shapes are only function and custom, and `tools` is on the denylist. OpenAI needs `web_search`, `file_search`, `code_interpreter`, `image_generation`, `mcp` (with secrets), `shell`, `apply_patch`, `local_shell`, `computer`, `namespace`, `tool_search`, `programmatic_tool_calling`. Even function/custom entries carry OpenAI-only extras: `strict`, `defer_loading`, `allowed_callers`, `async`, `output_schema`. Need (a) tool-level `providerOptions` merge, and (b) a way to append native tool entries (for example `providerOptions.tools` appended after our tools, with the denylist applying to overwrite, not append). Changelog mentions a web-search field (`return_token_budget`) the spec lacks, so tool entries should be pass-through objects, not closed types.
2. **Tool results need per-provider extras.** `function_call_output` may need `caller` (programmatic tool calling), `name`, `namespace`; result kinds beyond function/custom (shell, apply_patch, computer, MCP approval, tool-search output) are not text/image/file parts. Need message-level `providerOptions` on `tool_result` and `native` messages for the structured ones. The shared `tool_result` has no place for an error flag, and OpenAI has none either (fold into text).
3. **Tool-call kind resolution.** `tool_result` -> `function_call_output` vs `custom_tool_call_output` requires remembering the call's kind; since assistant items are kept verbatim, the adapter must scan prior native items by `call_id`.
4. **Stop reason is derived, not given**, and the "pending call" test depends on matching output items; `pause_turn` is only a heuristic.
5. **`store` default `true`** at OpenAI vs "gateway never stores". It is the caller's choice per our design, but the default silently leaves a 30-day copy at OpenAI. Also `background:true` is unusable and `item_reference`, `previous_response_id`, `conversation` only work with stored state.
6. **`output_text` plus `phase`.** Concatenating all text mixes commentary with final answer. Phase must be preserved verbatim on replay (docs warn degraded behaviour otherwise), which verbatim replay does automatically.
7. **Replay is not exactly verbatim.** Strip `created_by`; drop failed computer outputs and non-completed custom outputs; drop non-developer `additional_tools`. Reasoning and `program` items must be round-tripped intact (`encrypted_content`, `fingerprint`).
8. **`prompt` (deprecated, shutdown 2026-11-30)** makes `model`/`input` optional, contradicting the assumption that those are always owned.
9. **No audio input** in the Responses union despite stale text in the spec.
10. **`file_id` sources** (image/file) are not url/base64. Needs `providerOptions` or native.
11. **Credentials in the body.** `mcp.authorization`, `mcp.headers` and `container_auto.network_policy.domain_secrets[].value` are secrets passed in `tools`. A gateway that logs request bodies must redact them.
12. **Long non-streaming requests.** Reasoning-heavy calls can run for minutes; OpenAI's answer is `background` or streaming. Our no-streaming rule means one long-held HTTP connection through the Worker. An internal-stream-then-aggregate option would be an implementation choice, noted only as a risk.
13. **Cost**: not in usage. Must be computed, with cache-write rates and service tier (flex/priority/ultrafast) affecting price.
14. **Multi-agent (beta)** changes the output vocabulary (`agent_message`, `multi_agent_call`) and sits on a different path flavour plus beta header. Unsupported for now.

## 9. HTTP errors

`ErrorResponse = {error: {type*, message*, param*|null, code*|null, misalignment?}}`. Status codes in the spec for create: 400 (invalid or incompatible parameters), 404 (model or referenced resource not found or unavailable), 429 (`InferenceRateLimited`), 503 (`InferenceServiceUnavailable`). Changelog 2026-09-02: `429` with code `slow_down` (traffic ramped too fast) vs `503` with `server_is_overloaded`; both may carry `Retry-After`, so wait at least that long, else exponential backoff. 429 also covers credit/spend/usage limits (distinct codes in error-codes guide). Also `400` for an invalid `service_tier`. Request-level safety blocks can also arrive as 200 `status:"failed"` + `Response.error` (codes in section 4).

## 10. Streaming and event vocabulary (out of scope; for refusal text only)

`stream:true` returns SSE with `response.created`, `response.in_progress`, `response.output_item.added/done`, `response.output_text.delta/done`, etc. (`ResponseStreamEvent`). Not needed, but the final `response.completed`/`response.incomplete`/`response.failed` payloads carry the same `Response` object as the non-streaming reply.
