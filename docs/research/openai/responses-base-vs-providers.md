# Responses format base versus provider profiles

**Research date: 2026-10-11.** This report preserves the proposed design: a stateless Cloudflare Worker gateway, a lightweight TypeScript SDK with handwritten types and no runtime provider SDKs, one non-streaming `complete` endpoint, native request options, and provider output items retained and replayed unchanged. Recommendations below concern the adapter/profile boundary, not a redesign.

**Evidence standard.** Findings come from official specifications, provider documentation, published OpenAPI schemas, and provider-maintained implementation source fetched using `curl`, plus a shallow clone of the official Open Responses repository under `/tmp/acentric-research`. No authenticated inference requests or acceptance tests were run. “Documented” means a primary source says it is supported; a schema entry alone means “schema-listed,” not demonstrated behavior. **U = unverified** in the inspected sources; **conflict** means official sources disagree. Proposed library behavior is explicitly identified as a recommendation rather than a provider guarantee.

## 1. Conclusions that affect the split

1. **Open Responses is real.** Its official site is [openresponses.org][ors], its repository is [openresponses/openresponses][orr], and it launched on **2026-01-15**. The latest dated specification inspected is **2026-04-24**, which adds WebSockets, standalone compaction, assistant `phase`, and optional output logprobs. The checked-out repository commit is `7078a8f1aecd3d1cd41c9891e21c307fcda7f4af`. [Changelog][orc]; [versioned specification][orv]; [pinned repository][orp].
2. **A common schema is not a universal capability guarantee.** Open Responses includes `store`, `previous_response_id`, `reasoning`, `background`, `service_tier`, `prompt_cache_key`, and other fields, but real Responses-compatible providers implement different subsets. OpenRouter explicitly rejects stored continuation; Groq is stateless; xAI labels some fields compatibility-only. Separate **shared wire vocabulary**, **implemented capabilities**, and **provider/model semantics**. [Open Responses schema][oro]; [OpenRouter overview][ore]; [Groq guide][grg]; [xAI schema][xas].
3. **Do not force Fireworks `store=true`.** Current Fireworks documentation explicitly permits `store=false`; storage defaults to true, stored data expires after 30 days, and an unstored response cannot be used as `previous_response_id`. Its reference allows the response `id` to be null when unstored. [Fireworks guide][fwg]; [retention policy][fwd]; [reference][fwr].
4. **Do not assume Fireworks emits an item with literal `type:"tool_call"`.** Its published schema has a component named `ToolCall`, but describes the discriminator as `function_call` or `mcp_call`. It separately lists **`tool_output`** with `tool_call_id`, which is a real schema-level deviation from the usual function-result shape. The current guide additionally documents `reasoning` and `web_search_call`. Literal `tool_call` emission is **U**, not a verified compatibility requirement. [Fireworks reference][fwr]; [guide][fwg].
5. **Compaction, background execution, prompt-cache keys, service-tier fields, and encrypted reasoning are not inherently OpenAI-only.** Several are in Open Responses itself or implemented by other providers. OpenAI's exact parameters, hosted implementations, retention behavior, and extra resources remain provider-specific. [Open Responses changelog][orc]; [schema][oro]; [Fireworks guide][fwg]; [xAI Responses reference][xar]; [Azure guide][azg].

## 2. Open Responses: scope and actual standardization

### 2.1 What the project specifies

Open Responses describes an interoperable interface based on OpenAI Responses: **items in → items out**, polymorphic item types, item/response lifecycles, semantic streaming events, function invocation, reasoning state, multimodal input, and provider extensions. Its public materials describe a schema and tooling ecosystem; the repository contains TypeSpec/OpenAPI, reference documentation, a browser acceptance tester, and a CLI tester. It does not require using a provider SDK or prescribe this library's gateway architecture. [Specification][ors]; [repository README][orr].

For HTTP, the spec requires JSON request bodies with `Content-Type: application/json`, documents required `Authorization`, and requires JSON responses for non-streaming requests. SSE and WebSocket rules also exist, but are outside the current library transport scope. The OpenAPI paths are `/responses` and `/responses/compact`; the `/v1` prefix comes from deployment/base-URL conventions, not from those path keys. [Versioned specification][orv]; [OpenAPI][oro].

### 2.2 Core request vocabulary

The following is the **complete top-level `CreateResponseBody` field inventory in the inspected Open Responses schema**, not a claim that every named provider honors every field. Notably, the schema has **no top-level `required` array** for this object; do not infer a “minimum required fields” rule from conventional examples. The library can still require model/input according to its own shared API and provider requirements. [OpenAPI, `CreateResponseBody`][oro].

| Group                       | Fields in the Open Responses schema                                                                                        | Semantics and portability limits                                                                                                                                                |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Selection and context       | `model`, `input`, `instructions`                                                                                           | `input` is a string or item array; a string represents a user message. `instructions` is a separate instruction string.                                                         |
| Native continuation         | `previous_response_id`, `store`                                                                                            | Spec defines continuation over prior input + output + new input; real providers may decline persistence.                                                                        |
| Tool use                    | `tools`, `tool_choice`, `parallel_tool_calls`, `max_tool_calls`                                                            | Standard function tools and call/result items; provider-hosted tools are extensions. Exact limits and tool policies differ.                                                     |
| Text and generation         | `text`, `temperature`, `top_p`, `presence_penalty`, `frequency_penalty`, `max_output_tokens`, `top_logprobs`, `truncation` | `text.format` includes text, JSON object, JSON schema. Model/provider acceptance and limits differ. There is **no standard top-level `stop` field** here.                       |
| Reasoning and optional data | `reasoning`, `include`                                                                                                     | Shared reasoning effort/summary vocabulary; `include` enum contains `reasoning.encrypted_content` and `message.output_text.logprobs`. Emitting encrypted reasoning is optional. |
| Scheduling and transport    | `stream`, `stream_options`, `background`, `service_tier`                                                                   | Present in the schema even though this library only transports non-streaming HTTP. | Metadata, safety, cache     | `metadata`, `safety_identifier`, `prompt_cache_key`                                                                        | Shared field names; quotas, validation lengths, operational behavior differ.                                                                                                    |

Source for every row: [Open Responses OpenAPI][oro]. For example, its `max_output_tokens` minimum is 16, while Fireworks documents a minimum of 1; its service-tier enum is `auto/default/flex/priority`, while the prose allows providers to define their own tiers. This is another reason to avoid using the common schema as a universal runtime validator for provider-native options. [OpenAPI][oro]; [specification, service tiers][orv]; [Fireworks reference][fwr].

The output union also includes `function_call_output`; that does not mean every server emits external tool results in a create-response output. The schema lists `input_video` for function-result content, but ordinary user-message input is text/image/file. Do not advertise arbitrary audio/video support from the prose alone. [OpenAPI][oro].

There are documentation/schema rough edges: reasoning prose allows provider-defined raw content, but `ReasoningItemParam.content` in the inspected input schema is only null; prose calls reasoning fields optional, while the input schema requires `summary`. Preserve native reasoning and treat strict Open Responses schema validation as a separate diagnostic rather than rewriting valid provider output to fit that schema. [Reasoning prose][orv]; [OpenAPI][oro].

### 2.4 Extensions, tools, and conformance

The explicit item-extension rule is that provider-specific item types **MUST be prefixed with the canonical provider slug**, for example `openai:web_search_call`. Streaming-event extensions must also use the provider prefix. Function tools are the concrete standardized tool schema; hosted tools are described as an extensible pattern, with their execution/control-flow behavior explained. The inspected spec does **not** provide an equally complete typed arbitrary-hosted-tool registry, and its generated `ResponsesToolParam` currently resolves to `FunctionToolParam`. A generic tool object is therefore needed for native extension pass-through. [Specification, extensibility and tools][orv]; [OpenAPI][oro].

**No named conformance tiers or levels were found** in the official spec, README, or acceptance-test page. There is an acceptance suite that validates returned shapes against the OpenAPI and tests scenarios such as text, system prompts, function calling, image input, multi-turn history, `phase`, WebSockets, and compaction. Test filters are available, but filtering tests does not establish an official “Level 1/2/3” certification. No authoritative public table of dated per-provider full-suite results was found. [Acceptance tests][ort]; [README][orr]; [test implementation][ortsrc].

## 4. Concrete provider differences

### 4.1 OpenAI: reference implementation, not the base's full type universe

**Request fields.** The current create reference lists `access_programs`, `background`, `context_management`, `conversation`, `include`, `input`, `instructions`, `max_output_tokens`, `max_tool_calls`, `metadata`, `model`, `moderation`, `parallel_tool_calls`, `previous_response_id`, `prompt`, `prompt_cache_key`, `prompt_cache_options`, `prompt_cache_retention`, `reasoning`, `safety_identifier`, `service_tier`, `store`, `stream`, `stream_options`, `temperature`, `text`, `tool_choice`, `tools`, `top_logprobs`, `top_p`, `truncation`, and deprecated fields including `user`. Model-specific acceptance still applies; fields such as sampling and reasoning effort must not be promised for every OpenAI model. [Create reference][oac].

**Tools/items.** Functions use flat Responses definitions (`type/name/parameters/...`), not the nested Chat Completions `function` declaration. Custom freeform/grammar tools use `type:"custom"`, produce `custom_tool_call` with `input`, and accept `custom_tool_call_output`. Hosted/extended tools include web search, file search, code interpreter, image generation, computer use, remote MCP/connectors, shell, apply-patch, namespaces/tool search and related provider features. The exact catalog is OpenAI-native; do not make all its item types required base variants. Function strict mode has OpenAI-specific schema rules and defaults/fallback behavior. [Create reference][oac]; [function/custom-tool guide][oaf]; [tools guide][oat].

**State/reasoning.** `store` defaults true; stored response application state is normally retained for 30 days, with current docs saying at least 30 days and noting exceptions. `previous_response_id` works for continuation and cannot be combined with `conversation`; prior `instructions` are not carried forward when using continuation. `include:["reasoning.encrypted_content"]` permits stateless replay of opaque reasoning. Conversations are a separate durable resource whose items are not subject to the response object's normal 30-day TTL. [Create reference][oac]; [conversation state][oas]; [data controls][oad]; [reasoning guide][oar].

**Response semantics.** `usage` uses `input_tokens/output_tokens/total_tokens` and detail objects including cached/reasoning tokens. `max_output_tokens` includes both visible output and reasoning. Response statuses include completed, incomplete, failed, cancelled, queued, and in-progress; incomplete reasons include `max_output_tokens` and `content_filter`. A completed function call is an ordinary completed response containing a pending external action, not a response status of `tool_calls`. Refusal is a content part, not necessarily an HTTP error. [Create reference][oac]. HTTP error payloads and failed response `error` objects are different shapes; retain HTTP status and raw payload. [Error documentation][oaerr]; [create reference][oac].

### 4.4 OpenRouter

OpenRouter is a routing/translation layer, so capabilities depend on both router implementation and the selected upstream provider/model. It currently requires full history: `store:true` and non-null `previous_response_id` return **400**; `store` is `const:false` in the current schema. A response ID is not proof of reusable server-side context. [Overview][ore]; [OpenAPI][orschema].

**Schema-listed request fields:** `background`, `cache_control`, `debug`, `deferred_tools`, `frequency_penalty`, `image_config`, `include`, `input`, `instructions`, `max_output_tokens`, `max_tool_calls`, `metadata`, `modalities`, `model`, `models`, `parallel_tool_calls`, `plugins`, `presence_penalty`, `previous_response_id` (rejected non-null), `prompt`, `prompt_cache_key`, `prompt_cache_options`, `provider`, `reasoning`, `route`, `safety_identifier`, `service_tier`, `session_id`, `stop_server_tools_when`, `store` (false), `stream`, `temperature`, `text`, `tool_choice`, `tools`, `top_k`, `top_logprobs`, `top_p`, `trace`, `truncation`, `user`. Being schema-listed does not guarantee upstream support, especially background/prompt/hosted features. [OpenAPI `ResponsesRequest`][orschema].

Functions and custom tools are schema-listed, including grammar formats; hosted tools include standard OpenAI-shaped tools and explicitly namespaced router tools. Examples include **`openrouter:web_search`, `openrouter:web_fetch`, `openrouter:mcp`, `openrouter:tool_search`, `openrouter:shell`, `openrouter:subagent`, `openrouter:advisor`**, with matching namespaced output types and additional router-specific options. `defer_loading` and async execution have router/upstream-specific behavior. Keep these generic/native, not required base variants. [OpenAPI, request tools and `OutputItems`][orschema]; [tool guide][ortools]; [web-search guide][orsearch].

Reasoning effort and encrypted reasoning output are documented; preserve entire reasoning items because guide examples and schema variants differ in the representation of `summary`. HTTP failures generally use `error:{code:number,message,metadata?}`, with the number corresponding to HTTP status; Responses generation errors instead use string error codes with message and optional router metadata, and can occur inside a response. The native `provider.require_parameters:true` setting filters upstreams to those supporting the supplied parameters. [OpenAPI, `ProviderPreferences`][orschema].

### 4.8 vLLM

## 5. Proposed code split

This section is a **library design recommendation**, derived from the evidence above. It keeps the given design and uses provider profiles to make differences explicit.

### 5.1 What BASE means

Use **one `responses` format adapter**, with a conservative Open Responses vocabulary and permissive native pass-through. Separate two questions:

- **Grammar the adapter understands:** common message/function/result/reasoning/compaction shapes, input text/image/file encoding, the Responses envelope, statuses, standard usage, and error extraction. These are standardized shapes even when a provider cannot use every one. [OpenAPI][oro].
- **Features a particular request can rely on:** provider + model + deployment capabilities. There is no evidenced universal set that includes files, custom tools, hosted tools, encryption, or server-side state across all named providers. An API that rejects a normative continuation feature can be Responses-compatible for a subset without being shown fully compliant with the entire specification. [Spec][orv]; [provider evidence][ore]; [Groq][grg]; [Ollama][olg].

The lowest evidenced practical text subset is `model`, text `input`/message history, instruction text, synchronous non-streaming completion, message output with `output_text`, and the broad Responses envelope. Function-tool vocabulary is shared, but only enable it for tool-capable models and documented profiles. Reasoning, multimodal content, strict JSON, custom tools, and persistence are capability-gated. This is a portability recommendation, **not a newly invented conformance level**.

The handwritten common request type may name the Open Responses fields listed in §2.2, but must not become an exclusive allowlist. Native provider options remain the provider's own fields and are passed through. Keep provider-specific typed options separate from common format types; neither import official SDKs nor require a runtime schema package. Unknown values/items remain available as native JSON. “Verbatim” here means preserving JSON fields/values/order of items, not retaining original HTTP whitespace.

### 5.3 Native requests and narrow profile validation

Recommended request flow:

1. Construct only the fields owned by shared mapping (`model`, mapped `input`, optional mapped instructions/tools as applicable).
2. Apply provider-native options without renaming their fields. Define and document precedence for overlap; do not silently overwrite native input or append duplicate mapped history. Ambiguous shared/native combinations can be rejected as a library input error.
3. Validate **documented** required/forbidden combinations for that provider, using a narrow profile hook. No global OpenAI-only allowlist and no stripping unknown provider keys.
4. Send non-streaming HTTP (`stream:false` according to this endpoint's contract) with profile URL/auth. If a caller provides incompatible streaming options, surface an explicit conflict rather than silently forwarding an SSE request.
5. Parse minimally and return native items/envelope plus shared extractors. A caller's native `background:true` can return queued/in-progress status; it does not authorize adding polling/retrieval endpoints to the library. Expose pending accurately rather than call it a completed answer.

This distinguishes the fixed library transport contract from native generation/storage/scheduling choices. `store:false` must remain an explicit native option where supported, not inferred from the worker being stateless. A stateless worker can call a stateful upstream without keeping local state. [Spec persistence distinction][orv]; [Fireworks storage][fwg]; [OpenAI background][oabg].

### 5.4 Base parsing and stop-reason extraction

Preserve `response.output` exactly; extract shared views without changing it. Do not assume `output[0]` is a message or that HTTP JSON has the SDK's `output_text` convenience property. Join text from appropriate message `output_text` parts in item order; expose phase/role-aware views if needed, keep reasoning summaries separate, and preserve refusal distinctly. [OpenAI reference][oac]; [Open Responses items][orv].

Recommended derived stop mapping (names may be adapted to the library's existing enum):

| Native evidence                                          | Shared derived meaning         | Important distinction                                                                         |
| -------------------------------------------------------- | ------------------------------ | --------------------------------------------------------------------------------------------- |
| Non-2xx HTTP response                                    | Request/provider error         | Capture status, headers/request ID where present, raw body, and parsed fields.                |
| `status:"failed"` or non-null generation `error`         | Generation error               | Can occur in an otherwise successful HTTP response.                                           |
| `status:"cancelled"`                                     | Cancelled                      | Preserve raw status; don't call it normal end.                                                |
| `queued`, `in_progress`, Fireworks `cancelling`          | Pending / cancellation pending | Do not synthesize final completion or poll implicitly.                                        |
| `incomplete`, reason `max_output_tokens`                 | Output limit                   | Keep partial items and raw reason.                                                            |
| `incomplete`, reason `max_tool_calls`                    | Tool-call limit                | Fireworks extension; it is not a request to execute another tool.                             |
| `incomplete`, reason `content_filter`                    | Filtered                       | Different from an assistant refusal content part.                                             |
| `incomplete`, xAI `max_prompt_tokens` / `max_time_limit` | Context limit / time limit     | Profile-known reasons; preserve raw reason even if common enum is generic.                    |

The priority should be transport/generation failure → incomplete/pending/cancelled → pending external action → completed. An incomplete function-arguments fragment should not become an automatically executable function call just because it has `type:"function_call"`.

**Usage:** base reads standard `input_tokens`, `output_tokens`, `total_tokens`, optional `input_tokens_details.cached_tokens`, `output_tokens_details.reasoning_tokens`; retain the complete native usage object. Missing means unknown, not zero. Never add reasoning to output counts by default or recompute provider totals. For Fireworks only, fall back to `prompt_tokens/completion_tokens` if standard keys are absent, tagging the observed vocabulary if useful. Extra costs/cache writes/source/tool/per-turn details remain native or profile extractors. [Open Responses usage][oro]; [Fireworks reference][fwr]; [xAI example/schema][xar]; [OpenRouter][orschema]; [vLLM][vlp].

**Errors:** base should distinguish HTTP error envelopes from generation `response.error`. Common extraction can read nested `error.message/type/code/param`, while accepting numeric or string codes. A profile hook handles Fireworks 422 `detail`, Azure filtering extensions, and any actually observed nonstandard envelope. If parsing fails or the body is HTML/plain text, preserve raw body/status; do not claim a provider schema violation hides the underlying failure. Schema-listed optional fields must not be required to produce a useful error. [Spec errors][orv]; [Fireworks][fwr]; [OpenRouter errors][orerr]; [Azure][azg]; [Groq][gre].

```ts
  validateRequest?(request: JsonObject): void;
  encodeFileData?(base64: string, mime: string, filename: string): JsonObject;
  extractUsage?(response: JsonObject): JsonObject | undefined;
  extractError?(httpStatus: number, body: unknown): JsonObject | undefined;
  extractClientCalls?(items: readonly JsonObject[]): readonly JsonObject[];
}
```

Keep hooks sparse: authentication, documented request validation/combinations, file-byte representation, and extractor deviations. Avoid a general response-rewrite hook: the original output items are the replay source of truth. A Fireworks usage/error extractor changes a shared view, not the native object. Native hosted definitions can stay generic without making the SDK depend on every provider tool schema.

## 6. What belongs to OpenAI's profile rather than BASE

“OpenAI-only” should mean **OpenAI-native semantics or a feature absent from the common schema**, not necessarily an exclusive capability no competitor offers.

| Feature                                | Correct classification                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OpenAI hosted tools and resources      | OpenAI profile/tool types: exact web/file/code/image/computer/MCP/shell/patch definitions, vector stores, containers, connectors, approvals, annotations, execution policy, output item shapes. Other providers can offer similarly named tools with different behavior. [OpenAI tools][oat]; [xAI][xas]; [Fireworks][fwg]                                                          |
| `conversations` and `conversation`     | Not in inspected Open Responses create schema; OpenAI/Azure/Foundry resource feature, with native persistence semantics. [OpenAI state][oas]; [OpenAPI][oro]; [Azure][azr]                                                                                                                                                                                                          |
| `prompt` reusable prompt registry      | Outside common request schema; preserve as OpenAI-native (also schema-listed elsewhere with provider-specific support). [OpenAI][oac]; [OpenAPI][oro]                                                                                                                                                                                                                               |
| Prompt caching                         | `prompt_cache_key` is **common**, not OpenAI-only. OpenAI `prompt_cache_retention`, `prompt_cache_options`, TTL/breakpoints and content `prompt_cache_breakpoint` rules are native extensions/semantics. OpenRouter has its own cache control; xAI uses the key for routing. [OpenAI caching][oacache]; [OpenAI reference][oac]; [OpenAPI][oro]; [OpenRouter][orschema]; [xAI][xas] |
| Service tiers                          | Field is **common**; OpenAI accepted values, pricing/access/model behavior are profile-specific. Current OpenAI reference includes fast/priority and ultrafast semantics beyond the dated common enum. Other providers have their own tiers. [OpenAI][oac]; [spec][orv]; [xAI][xas]; [Groq][grr]                                                                                    |
| Background                             | Field is **common**, Fireworks/Azure implement it. OpenAI's background retention/ZDR/poll/cancel behavior is native. The non-streaming library need not add polling. [OpenAPI][oro]; [OpenAI background][oabg]; [Fireworks][fwg]; [Azure][azg]                                                                                                                                      |
| Compaction                             | **Now common** as item and standalone endpoint, April 24. OpenAI automatic `context_management` and exact compaction/model behavior are provider extensions; xAI has compact too, while its context-management directives are parsed but not executed. [Changelog][orc]; [OpenAPI][oro]; [OpenAI][oac]; [xAI][xas]                                                                  |
| `phase`                                | Now common optional assistant-message field; preserve it verbatim. Not an OpenAI-only field to strip from generic history. [Changelog][orc]; [OpenAPI][oro]                                                                                                                                                                                                                         |
| Encrypted reasoning                    | Common optional vocabulary, not OpenAI-only cryptography. Ciphertext format/keys, model compatibility, include policy, storage, and replay are provider-specific. [Spec][orv]; [OpenAI][oar]; [xAI][xarg]                                                                                                                                                                           |
| Custom/grammar tools                   | Absent from current core function-only tool union; OpenAI extension serialization can be reused for documented adopters, such as OpenRouter. Do not promise all Responses providers support them. [OpenAPI][oro]; [OpenAI][oac]; [OpenRouter][orschema]                                                                                                                             |
| Safety identifiers/metadata            | Common field names; OpenAI constraints and enforcement semantics are provider-specific. xAI metadata is compatibility-only. [OpenAPI][oro]; [OpenAI][oac]; [xAI][xas]                                                                                                                                                                                                               |

[OpenAI create][oac]                                                                                                                                                                                                                              |
| Provider response-management endpoints | Retrieve/delete/input-items/conversations/compact are additional operations, not required SDK endpoints just because native IDs/options exist. Fireworks additionally lists responses; Foundry project API also lists responses. [Fireworks][fwg]; [Foundry project][azp]; [OpenAI][oas]                                                                                            |

## 7. Risks and verification priorities

1. **Ignoring fields versus rejecting them.** This is observed behavior, not a theoretical concern: xAI silently ignores some logprob include/model options and parses-but-does-not-execute context management; vLLM silently disables storage by default; Ollama ignores include and does not implement tool choice; Fireworks `defer_loading` has no effect; OpenRouter rejects stored continuation. Never infer support from a successful request or echoed response field. [xAI][xas]; [vLLM][vls]; [Ollama][ols]; [Fireworks][fwg]; [OpenRouter][ore].
2. **Unknown fields need an evidence-based policy.** No universal Responses unknown-field behavior was established. Pass native options through, reject only known unsupported or structurally incompatible combinations locally, and surface provider rejections with their raw body. Closed runtime validation based on OpenAI's types would discard extensions or reject valid provider inputs. [Spec extensibility][orv]; [router extensions][orschema].
3. **Native replay is provider-bound.** Retaining all output items is essential, but it cannot promise ciphertext, resource IDs, or hosted items work across providers/models/accounts. OpenAI/xAI explicitly discuss reasoning replay; Fireworks hosted replay coverage is incomplete. Do not strip IDs/status/phase or remove “irrelevant” reasoning when replaying. [OpenAI][oas]; [xAI][xarg]; [Open Responses][orv]; [Fireworks][fwr].
4. **The word “encrypted” is not a security contract.** The spec makes representation/cryptography provider-defined, and current Ollama code uses plain text in `encrypted_content`. Keep it opaque, preserve it, and report security characteristics only when independently documented. [Spec][orv]; [Ollama source][ols].
5. **Storage and gateway state are separate.** OpenAI/Fireworks default to upstream storage; Groq/OpenRouter do not; vLLM storage depends on deployment flags; Azure project state has separate scope. Avoid both an automatic `store=false` rewrite and an automatic `store=true` requirement. [OpenAI][oad]; [Fireworks][fwd]; [Groq][grr]; [OpenRouter][ore]; [vLLM][vls]; [Foundry][azp].
6. **Cost controls have different meanings.** xAI excludes reasoning/function tokens from `max_output_tokens`; OpenAI includes reasoning. Fireworks tool-limit incompletion differs from an ordinary external call, and OpenAI's built-in-tool cap differs from other providers' agent-turn limits. Shared option names must retain native semantics. [xAI][xar]; [OpenAI][oac]; [Fireworks][fwr].
7. **Schema and guide drift are material.** Fireworks usage/union/reference lag, Groq state/tool/truncation conflicts, and Ollama state bullets versus source mean one extracted schema cannot establish all runtime behavior. Record evidence/version/confidence alongside capability flags. [Fireworks][fwg]; [fwr]; [Groq][grg]; [grr]; [Ollama][olg]; [ols].
8. **File handling is especially nonportable.** Common shape does not guarantee MIME/size/inline-byte acceptance or a Files API. Ollama explicitly rejects files, xAI adds MIME metadata, and Azure has upload-purpose differences. Keep one completion endpoint and do not invent automatic uploads. [Ollama][ols]; [xAI][xas]; [Azure][azg]; [OpenAI files][oapdf].
9. **Errors/statuses must remain open-ended.** Numeric router error codes, Fireworks validation lists, Groq 498, Azure filter arrays, xAI time/context reasons, and provider-added statuses are all outside a narrow OpenAI-only parser. [OpenRouter][orerr]; [Fireworks][fwr]; [Groq][gre]; [Azure][azg]; [xAI][xas].

### Suggested first live compatibility fixtures (not run in this research)

| Fixture                                                   | What it would settle                                                                                               |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| OpenAI/Fireworks text + full-history replay               | Native output items remain unchanged; text/usage/status parsing works.                                             |
| Fireworks `store:false`                                   | Actual response-ID nullability and usage spelling; prove no unnecessary storage default is imposed by the library. |
| Function call → result → final answer, both providers     | Flat declarations, `call_id`, argument string preservation, namespace/deprecated function fields.                  |
| Fireworks MCP/SSE/web-search history replay               | Actual hosted output types and whether complete native output is accepted as input.                                |
| Fireworks reasoning + encrypted include rejection         | Verify always-on summary behavior and actual unsupported include response.                                         |
| Fireworks invalid schema / missing required field         | Observe whether 422 validation-detail envelope is still used alongside OpenAI-style errors.                        |
| Image URL/data URL and file URL/base64 per provider/model | Populate unknown capabilities with actual supported encodings/MIME limits.                                         |
| Token exhaustion + hosted tool cap + refusal/filtering    | Distinguish incomplete causes, refusal parts, pending external calls, and provider errors.                         |
| Unknown harmless request field                            | Record explicit ignore/reject behavior; do not treat acceptance as semantic support.                               |

**Final recommendation:** implement the Responses adapter around the common item/envelope grammar, keep generated shared mappings small, preserve native options/output without a closed OpenAI union, and make provider profiles carry capability evidence plus narrow validation/extractor hooks. OpenAI needs its rich native extensions; Fireworks mainly needs explicit supported tool/include lists, always-on-summary semantics, possible usage/error fallbacks, and no forced storage. Add other providers as profiles only for their documented/tested subset; Together/Mistral require endpoint evidence before joining this format.
