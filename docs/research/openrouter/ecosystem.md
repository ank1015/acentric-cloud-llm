# OpenRouter in LLM libraries: integration patterns and known pitfalls

Verified 2026-10-12.

Method: shallow clones of four repos, read from source (no install or build scripts run), npm registry checks, GitHub issue searches and reads via `gh`, and the OpenRouter docs pages `reasoning-tokens`, `usage-accounting`, `errors-and-debugging`, `provider-routing` and `prompt-caching`. The docs pages were read through a summarizing fetch, so their wording here is paraphrased. Line numbers refer to the commits below. Runtime behavior was not tested against the live API. Findings rest on reading code and issue reports.

Related: `usage-cost-catalog.md` in this folder covers usage fields and the model catalog from the API side.

## 1. Key findings

1. Most libraries use `POST /api/v1/chat/completions`. The TS SDK's `callModel` uses `/api/v1/responses`. pi sends `anthropic/*` models to OpenRouter's Anthropic Messages route (`https://openrouter.ai/api`).
2. Only the ai-sdk provider and pi replay `reasoning_details` across turns. LiteLLM's OpenRouter module never reads or writes it (zero hits under `litellm/` outside tests).
3. Errors arrive as HTTP 200. The ai-sdk provider checks for them on both stream and non-stream paths. pi never reads the stream `error` field, so its message is lost.
4. Cost: the ai-sdk provider and TS SDK expose OpenRouter's returned `usage.cost`. pi computes cost from its own static catalog and ignores the response cost. LiteLLM reads cost for non-streamed responses only.
5. The biggest real-world breakage is provider-scoped encrypted reasoning (Gemini thought signatures, OpenAI encrypted reasoning) when OpenRouter switches the upstream provider mid-conversation.

## 7. Not verified or limits

- No live API calls. All behavior is from source and issue reports.
- Issue states are as of 2026-10-12. Keyword search can miss issues.
- Docs quotes come from a summarizing fetch; wording is paraphrased.
- LiteLLM non-stream error handling and `thinking` mapping were not fully traced.
- ts-sdk "200 with error fails validation" is inferred from the schema.

## Lessons for us

- Replay `reasoning_details` exactly as received: same order, unmodified, including empty arrays. Store it as opaque JSON per assistant message. Never rebuild signatures from text.
- For tool-call continuations that carry Gemini or OpenAI encrypted reasoning, pin the upstream (`provider.order` with `allow_fallbacks: false`) or be ready to drop encrypted blocks and retry. A provider switch is the main cause of 400 "Corrupted thought signature".
- Check every response for a top-level `error`, in stream chunks and in non-stream bodies, before reading `choices`. Surface `error.message` and `metadata.raw`. Do not map `finish_reason: "error"` to a bare error string.
- Retry only on transient failures. pi shows the cost of not retrying `finish_reason: "error"` (#9002). Retries of requests that already produced billed output also cost money, so cap them and log each attempt.
- Never replace invalid tool-call JSON with `{}`. Fail the call or repair explicitly. Detect premature EOF (ai-sdk #558, #573).
- Use the response `usage.cost`, `cost_details.upstream_inference_cost`, and `is_byok` as the cost of record. Treat static catalog prices as estimates (pi #9980).
