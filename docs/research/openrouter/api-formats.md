## 1. Endpoints and format choice

OpenRouter is a translator and router. Its native response is **OpenRouter's output in the selected API format**, not necessarily the upstream provider's original output. Preserving that output is necessary for replay, but does not undo translation already performed inside OpenRouter. [API overview][overview].

**Recommendation from OpenRouter:** its general quickstart still starts with Chat Completions. Responses is advertised as an OpenAI-compatible replacement, and its own SDK/agent ecosystem also uses it. I found no current blanket recommendation to migrate every application from Chat to Responses. The explicit migration recommendations are `responses` over the SDK beta alias, and `openrouter:web_search` over the deprecated web plugin. [Quickstart][quick]; [Responses overview][responses]; [web search][web].

## 2. Responses: requests, outputs and OpenAI differences

### Request field inventory

This is the complete top-level `ResponsesRequest` property inventory in the downloaded schema. Neither it nor its `input` field is marked required there; the overview's missing-model error shows why this is not sufficient validation guidance. [Spec][spec]; [overview][responses].

| Group                          | Schema-listed fields                                                                                                                                              |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Model and context              | `model`, `models`, `input`, `instructions`, `prompt`                                                                                                              |
| State and execution            | `store`, `previous_response_id`, `background`, `stream`, `service_tier`                                                                                           |
| Generation                     | `max_output_tokens`, `temperature`, `top_p`, `top_k`, `top_logprobs`, `frequency_penalty`, `presence_penalty`, `text`, `truncation`, `modalities`, `image_config` |
| Reasoning and output inclusion | `reasoning`, `include`                                                                                                                                            |
| Tools                          | `tools`, `tool_choice`, `parallel_tool_calls`, `max_tool_calls`, `stop_server_tools_when`, `deferred_tools`                                                       |
| Routing and plugins            | `provider`, `route`, `plugins`                                                                                                                                    |
| Caching                        | `cache_control`, `prompt_cache_key`, `prompt_cache_options`                                                                                                       |
| Metadata and identification    | `metadata`, `user`, `safety_identifier`, `session_id`, `trace`, `debug`                                                                                           |

Important acceptance distinctions:

- `store` is literally `const:false`, default false. Omission or false is the documented stateless path. Non-null `previous_response_id` is refused, not ignored. An ID in a response does not enable stored continuation. [Responses overview][responses].
- `background` is schema-listed, but no usable background/retrieval workflow is established. Our existing adapter already refuses `background:true` and `stream:true`; retain that contract independently of upstream behavior.
- `reasoning` lists `effort`, `summary`, `context`, `mode`, plus router `enabled` and `max_tokens`. `effort` lists `none/minimal/low/medium/high/xhigh/max`; each model accepts a subset. Responses schema **does not list `exclude`**, although the general reasoning guide documents it. Do not silently claim Responses exclusion support. [Spec][spec]; [reasoning][reasoning].
- `include` lists exactly `file_search_call.results`, `message.input_image.image_url`, `computer_call_output.output.image_url`, `reasoning.encrypted_content`, `code_interpreter_call.outputs`. OpenAI's additional search-source/result and output-logprob include values are absent. Their reject/ignore/pass-through behavior is unverified. [Spec][spec]; [OpenAI create][oa-create].
- `text.format` lists text/JSON object/JSON schema; `text.verbosity` extends to `xhigh`/`max`. Structured-output enforcement is endpoint-dependent, even with `strict:true`. [Spec][spec]; [structured output][structured].
- Known ignored settings include tool `async` on providers without async support and `max_tool_calls` when `stop_server_tools_when` is supplied. Unsupported model parameters may also be ignored by default routing. [Spec][spec]; [routing][routing].
- `prompt`, compaction/item-reference inputs, and OpenAI-shaped hosted tool declarations are schema-listed. That is not evidence of OpenAI prompt IDs, vector stores, encrypted compaction, or hosted resources working on OpenRouter. [Spec][spec].

**Reasoning by model family:** OpenAI models can return summary and encrypted reasoning; request `include:["reasoning.encrypted_content"]` for stateless reasoning replay. Claude-style reasoning can carry raw/visible thinking plus `signature` and `format:"anthropic-claude-v1"`; this is explicitly represented by the router's SDK type/example. Gemini has `format:"google-gemini-v1"` available, but the Responses guides provide no exhaustive model-by-model mapping of Gemini thought signatures into `content`, `signature`, or `encrypted_content`. The Chat integration source explains Gemini uses opaque encrypted continuity rather than the SDK's explicit signature field (see §3); do not infer that Responses uses precisely the same packing. [Reasoning context][reasoning]; [SDK reasoning item][sdk-reasoning]; [official Chat converter][ai-convert].

`encrypted_content` can also carry **OpenRouter-owned deferred-tool state**, independent of whether the upstream model itself exposes reasoning. It is opaque protocol data, not an OpenAI-only field or a guarantee of cross-model cryptographic compatibility. [Tool search][tool-search].

### Usage, status and errors

Responses usage lists `input_tokens`, `output_tokens`, `total_tokens`, `input_tokens_details.{cached_tokens,cache_write_tokens}`, `output_tokens_details.reasoning_tokens`, plus `cost`, `is_byok`, `cost_details`, `server_tool_use_details`. Its cost breakdown uses **`upstream_inference_input_cost` / `upstream_inference_output_cost`**, whereas Chat's `CostDetails` uses **`upstream_inference_prompt_cost` / `upstream_inference_completions_cost`**; both may include `upstream_inference_cost` and `server_tool_cost`. Preserve raw usage, not just normalized token counts. Reported `cost` is the account charge in USD-denominated credits; it is different from our catalog token estimate. [Spec][spec]; [usage accounting][usage]; [support currency][support].

Overall status enum is `completed/incomplete/in_progress/failed/cancelled/queued`. `incomplete_details.reason` lists `max_output_tokens/content_filter`. Only completed/incomplete are finished answers in our contract. Pending client calls can occur in a completed response. Do not treat every incomplete hosted item as an incomplete whole response. [Spec][spec].

Native Responses error codes lose distinctions: context/request errors can become `invalid_prompt`; auth/availability/timeout can become `server_error`. Failed responses carry canonical **top-level `error_type`**. Preserve that and metadata, including deferred-tools subcodes, when mapping errors. HTTP-only status mapping is insufficient: a 403 can be a policy error, and 402 means insufficient credits. The docs also describe some length-related upstream errors converted into successful length stops. [Responses errors][response-errors]; [general errors][errors].

## 3. Chat Completions: native messages and replay

### Message shapes

The request is `messages:[...]`; roles are `system/developer/user/assistant/tool`. System/developer content is string or text-part array. User/tool/assistant content may be string or multipart; assistant content can be null. Native assistants additionally hold `name`, `model`, `tool_calls`, `reasoning`, `reasoning_details`, `refusal`, `images`, `audio`, and documented **`annotations`**, even though that last field is absent from the generated `ChatAssistantMessage` schema. [Spec][spec]; [PDFs][pdfs]; [web plugin citations][web-plugin].

| Content / tool shape    | Raw JSON                                                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Text/cache marker       | `{type:"text",text,cache_control?:{type:"ephemeral",ttl?:"5m"\|"1h"},prompt_cache_breakpoint?:{mode:"explicit"}}`          |
| Image                   | `{type:"image_url",image_url:{url,detail?}}`; remote URL or data URL; detail includes auto/low/high/original in the schema |
| File/PDF                | `{type:"file",file:{filename?,file_data?,file_id?}}`; guides put a URL or data URL in `file_data`                          |
| Audio input             | `{type:"input_audio",input_audio:{data,format}}`; base64 bytes, not a remote URL; supported formats depend on model        |
| Video input             | New `{type:"input_video",video_url,processing?}` and legacy nested `video_url` variants are schema-listed                  |
| Assistant function call | `{id,type:"function",function:{name,arguments}}`; `arguments` stays the original string                                    |
| Client result message   | `{role:"tool",tool_call_id,content}`; content may be multipart, subject to upstream support                                |

Sources: [image guide][images], [PDF guide][pdfs], [audio guide][audio], [video guide][videos], [spec][spec]. Per-part cache support in the Chat schema is explicit on **text**; function definitions also expose cache control. Do not infer every non-text part accepts every Anthropic block option. The current Files API gives workspace-scoped `or_file_...` handles, and schema fields accept file IDs, but per-format/model resolution still needs a live fixture. [Files][files].

### Reasoning configuration and details

The general guide documents `reasoning.effort`, `max_tokens`, `exclude`, `enabled`. Effort and budget are alternatives, not a promise both will be honored. `exclude:true` hides reasoning while tokens remain billed and normally share the output budget. The guide also documents `context` and `mode` for supported newer OpenAI models. **Current Chat OpenAPI/SDK expose only `effort` and `summary` inside `reasoning`**, a material schema/guide gap. `reasoning_effort` is a shorthand and conflicts with a different nested effort. Per-model `reasoning` metadata and endpoint `supported_parameters` are discoverable by GET. [Reasoning][reasoning]; [parameters][parameters]; [models][models]; [SDK Chat request][sdk-chat-request].

Plain `message.reasoning` is readable reasoning text (`reasoning_content` is a documented alias on replay). It cannot replace signed/encrypted structured details. Keep both fields when returned, including an explicitly empty `reasoning_details:[]`. The official AI SDK provider preserves empty arrays because some upstreams distinguish them from an omitted field. [Reasoning guide][reasoning]; [official converter][ai-convert].

| Detail `type`                | Payload                                                             | Common metadata                                                        |
| ---------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `reasoning.summary`          | `summary:string`                                                    | `id:string\|null`, optional `format`, `index`                          |
| `reasoning.encrypted`        | `data:string` (opaque)                                              | Same                                                                   |
| `reasoning.text`             | `text:string\|null`, `signature:string\|null` when present          | Same                                                                   |
| `reasoning.server_tool_call` | `tool_name`, `arguments`, `result` strings; optional `tool_call_id` | Same; newer schema extension beyond the guide's three-type description |

`format` currently lists `unknown`, `openai-responses-v1`, `azure-openai-responses-v1`, `bedrock-openai-responses-v1`, `bedrock-xai-responses-v1`, `xai-responses-v1`, `meta-responses-v1`, `anthropic-claude-v1`, `google-gemini-v1`, or null. Preserve it, IDs, index, payload and array order without interpreting ciphertext. [Spec][spec]; [reasoning details][reasoning].

The documented tool continuation is: original assistant content **plus all tool calls and unmodified reasoning details**, followed by matching tool results. Consecutive reasoning blocks must remain in the original sequence. The guide presents the same structure for Claude and OpenAI; its Gemini tool guide appends the **whole assistant message** before results. These are preservation rules, not a guarantee that every missing block will cause a particular error on every model. [Reasoning preservation][reasoning]; [tool calling][chat-tools].

| Model family                                 | What must remain opaque                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Anthropic                                    | Visible/summarized thinking in `reasoning.text` may carry explicit `signature`; redacted/encrypted state uses structured details. Official converter source describes invalid-signature failures after metadata loss. Raw reasoning text without its signed structure can reconstruct invalid thinking blocks.                                                                                                                                                                          |
| Gemini                                       | Official converter comments say Gemini does not use its explicit SDK `signature` field for continuity; `reasoning.encrypted` carries the opaque continuity blob. Edited thought text can produce a corrupted-signature error. The converter filters unsigned text and deduplicates details; its comments and filter implementation are not a universal wire contract. Our gateway should preserve raw OpenRouter output and test replay rather than adopt those lossy conversion rules. |
| OpenAI/Azure and related Responses upstreams | Summaries and encrypted details represent Responses reasoning. Preserve item IDs/format and ciphertext; do not reduce them to visible `reasoning`.                                                                                                                                                                                                                                                                                                                                      |

Failure, upstream ignoring/dropping, or explicit conversion may occur. New Claude guides also document model-binding mismatch reporting when the caller opts into `drop_block`. ### Annotations, refusal and stop metadata

- Preserve assistant `annotations` along with content. Web citations use OpenAI-style URL annotations. Parsed PDF annotations are `{type:"file",file:{hash,name?,content:[text/image parts]}}`; echoing them lets OpenRouter reuse parsing. Preserve `hash` and complete parsed content. The PDF example still includes the original input file on follow-up, despite prose suggesting it can be omitted; that omission is unverified. Errors after successful parsing may return `error.metadata.file_annotations`. [PDFs][pdfs]; [web citations][web-plugin].
- Preserve `refusal`; a successful model refusal can be `message.refusal` plus `finish_reason:"content_filter"`, while a policy/refusal error is a separate error path. [Errors][errors].
- `finish_reason` is normalized to `tool_calls/stop/length/content_filter/error` (nullable in schema). `native_finish_reason` preserves the upstream stop reason and is documented on each choice, **but omitted from the generated `ChatChoice` schema**. Keep both in result metadata; neither is part of the replayed assistant message. [Overview][overview]; [spec][spec].
- Keep actual returned model/upstream identity outside history as provenance. A routed response's model may differ from the requested alias/fallback slug. `usage`, generation ID, timestamps and choice logprobs are response metadata, not messages to append. [Overview][overview]; [router metadata][router-metadata].

## 4. What lossless replay requires

“Lossless” here means retaining and resubmitting the **OpenRouter-format conversation data**. It cannot promise an identical internal upstream transcript or model behavior.

| Format    | Save and replay                                                                                                                                                                                                                                                                                                       | Save separately / resend from caller                                                                                                                                                              |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Responses | **Every `output` item, in order, with every field**: message IDs/status/phase, content/refusal/annotations/logprobs, reasoning content/summary/signature/format/encrypted data, calls and opaque nested state, hosted tool actions/results/resource IDs. Append matching new result items, then the new turn.         | Envelope/usage/error/routing/model provenance; original full input, instructions and tool configuration. There is no response-ID history fetch.                                                   |
| Chat      | **Each selected `choices[i].message` object verbatim**, including null/empty fields, reasoning and full details, calls, annotations, images/audio, model/name/refusal and unknown additions. Append matching `role:"tool"` messages and new user turn. Choices are alternatives, not sequential turns to concatenate. | Finish/native finish reasons, usage, generation ID, provider/model provenance; original messages/instructions/tool configuration.                                                                 |
| Messages  | **Entire returned `content` block array** under `role:"assistant"`: thinking/signature, redacted data, text/citations, tool/server-tool blocks/results, compaction and router additions. Results answer tool-use IDs in user `tool_result` blocks.                                                                    | Envelope/stop/usage/routing; full history and top-level system/tools. Carry any required container/resource context in subsequent options; it is not automatically restored from the response ID. |

Sources: [Responses basic][basic], [tool results][response-tools], [Chat preservation][reasoning], [Messages input/output unions][spec]. Entire-output replay is the conservative implementation rule; the guides do not prove acceptance of every hosted output variant. In particular, current Messages output unions are broader than input block unions. Do not delete unknown blocks to make a schema validator happy; expose the provider error and verify the affected feature.

**Things that break or weaken replay:**

1. Keeping only text, rebuilding assistant messages from extractors, dropping empty arrays, annotations, reasoning, IDs/phase, or nested `subagent_items`.
2. Reordering reasoning/items, merging signed blocks, deduplicating by guessed keys, modifying thought text/ciphertext, or re-serializing call arguments. Normal JSON transport is necessary; do not promise byte-for-byte JSON key-order binding unless a specific protocol establishes it.
3. Changing model/provider/workspace, resolving a “latest” alias to a new model, or allowing router fallbacks to change upstream. Same OpenRouter account/format/model slug is helpful but is not proof of the same upstream route or signature compatibility.
4. Changing earlier history/system/tool configuration where prefix/model binding applies. Claude's current migration guide says Anthropic prefix enforcement is not generally applied to OpenRouter traffic; optional `drop_block` still reports removals via `input_transformations`. This does not waive router deferred-state checks. [Fable][fable].
5. Automatic context compression, plugin mutation/healing/alignment, truncation, model swapping or failed tool-state reconstruction. Some context compression is enabled by default on small-context endpoints (≤8192); explicit disabling is possible unless account policy enforces a setting. [Transforms][transforms]; [plugins][plugins].
6. Replaying unavailable workspace/provider files, expired sandbox context, or mismatched tool-call/result IDs. Resource handles are scoped; a schema field alone does not make them portable. [Files][files]; [tool guide][response-tools].

**Additional strict contract for `deferred_tools` v1:** all three formats carry router-owned state in reasoning (`reasoning_details`, `encrypted_content`, `redacted_thinking` respectively). Send history exactly as returned and keep `tools`, `tool_choice`, `deferred_tools`, tool order/descriptions/cache controls fixed. Prior edits, trimming/compaction or altered state break its chain; compression is disabled. Text-only partial interrupted turns can be kept, but tool calls without state are rejected. Error codes include `deferred_tools_state_missing`, `deferred_tools_state_invalid`, `deferred_tools_history_changed`, `deferred_tools_catalog_changed`; a different workspace also invalidates state. [Tool search][tool-search].

## 5. Mid-conversation system messages

All three current schemas allow system-shaped conversation entries: Chat system/developer messages, Responses system/developer input messages, and Messages `role:"system"`. **Schema permission is not a guarantee of native in-position system authority on every upstream.** [Spec][spec].

| Upstream                             | Established behavior / remaining uncertainty                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OpenAI Responses models              | System/developer items are represented directly; newer supported models also accept a separate `configuration_update` item for effort. Keep its position on replay.                                                                                                                                                                                                                 |
| Newer Claude models                  | Current Fable 5.1/Claude migration docs support inline system messages and `clear_at:"next_user_message"` in Messages. Keep the cleared message in history. This supersedes older blanket claims that Anthropic can never accept mid-conversation system messages. **Chat/Responses schemas do not expose `clear_at`**, so equivalent ephemeral-system support there is unverified. |
| Claude effort updates                | Responses `configuration_update`, Chat contentless system/developer `configuration_update`, and Messages system `output_config.effort` translate between formats. Before the first user, ordinary system text is moved to top-level `system` while the update stays inline; a text-plus-update entry is split. Updates unsupported by the model are rejected rather than dropped.   |
| Older Claude / arbitrary system text | No exhaustive translation rule was established for arbitrary system positions across older models/endpoints. Do not claim that all such messages stay inline, or that all are concatenated into top-level system.                                                                                                                                                                   |
| Gemini                               | Cache docs establish a single `systemInstruction` and normalized first system/developer prompt; its cached value is immutable. They do **not** establish how later system/developer entries are handled (hoisted, merged, rewritten, rejected). Native in-position system semantics remain unverified.                                                                              |

Sources: [reasoning effort updates][reasoning], [Fable migration][fable], [Gemini cache behavior][cache], [spec][spec]. Effort updates have placement/combination restrictions (no adjacent updates, no pro mode, no Responses `truncation:"auto"`); they are not ordinary system text. For our D3, gate genuine mid-conversation system support by verified model/route rather than a provider-wide boolean.

## 6. Strictness and silent changes

**Unknown fields:** the inspected request/message schemas usually omit `additionalProperties` rather than declaring false. Some nested objects are explicitly closed. This establishes no universal server reject/ignore rule. The parameter guide allows additional provider-specific fields, and names some it forwards, but does not guarantee arbitrary unknown fields are forwarded. The generated SDK uses known-field `z.object` serializers/remapping without catchalls on key messages; it is not a safe raw-output preservation layer. For example, annotations and native finish reasons documented elsewhere are missing from those types. Use our dependency-free raw JSON transport. [Spec][spec]; [parameters][parameters]; [SDK assistant serializer][sdk-assistant].

**Unsupported recognized parameters:** by default, endpoints can receive a request while unsupported parameters are ignored. `provider.require_parameters:true` filters to endpoints advertising support for submitted LLM parameters; when none qualify, routing fails. It is not a per-field proof of exact semantics and cannot prove support for unknown extension fields, nested flags or all content parts. Defaults softly prefer endpoints supporting tools, response format and verbosity, but if no endpoint for a candidate model supports one, that model can still be used and the parameter ignored. [Routing][routing].

Other concrete limitations:

- Anthropic strict function tools require supported `x-anthropic-beta: structured-outputs-2025-11-13`; docs say OpenRouter **strips `strict` without it**. JSON-schema response formatting receives automatic header handling. `require_parameters` is not documented to cure the missing strict-tool header. [Provider headers][routing].
- Structured-output `strict:true` guarantees depend on endpoint implementation. Some providers translate it or use the schema as a strong hint. [Structured outputs][structured].
- Async tools may be ignored on other endpoints; native `defer_loading` without router search may be expanded, passed in full, or refused, depending on model/route. [Spec][spec]; [tool search][tool-search].
- Plugin/account defaults can mutate requests/responses. Organization “Prevent overrides” settings can prevent disabling them; no request field universally makes this a transparent proxy. [Plugins][plugins].
- `provider.allow_fallbacks` defaults true; model fallback lists can additionally change models. Sticky sessions are best-effort. Explicit exact endpoint selection and disabling fallbacks are caller policy, not defaults our gateway should inject. [Routing][routing]; [cache][cache].

## Implications for our gateway

**Adapt Responses first as a separate OpenRouter profile**, using the common Responses format; add a separate Chat provider ID when per-block TTL, broad multimodal compatibility or Chat-specific clients matter. Consider Messages as another profile for Claude/native-block use after dedicated replay tests. Do not label one OpenRouter ID as multiple formats, and do not treat OpenRouter output as direct Anthropic/OpenAI output for cross-provider replay.

What can be reused: request input/user/image/file mapping, flattened function declarations, ordinary function/custom-result mapping, output retention, text/call extraction, finished-status handling, and standard token fields. Existing Responses call extraction already distinguishes native calls and results answered within a response. Extend native types with router items/fields while keeping them open; do not import SDK validators.

**Small changes are necessary before calling this a working profile:**

- Profile validation for known state refusal, unsupported per-block Responses `cache_control`, feature/route restrictions and D3 system semantics. The current profile has no request-validation hook; merely adding URL/headers is insufficient for those checks. Require callers who need strict capability selection to supply `provider.require_parameters:true`; never insert it silently.
- The existing Responses builder strips `created_by` from every assistant output item. That is an OpenAI-specific behavior, not established for OpenRouter. Make such replay exceptions provider-specific and evidence-based; do not otherwise rewrite router output.
- Read canonical `error_type` and router metadata before lossy native error codes. Current `classifyError` receives only status/code/type/message, so it cannot see top-level `error_type`; error reading needs a narrow extension. Preserve full failure body and any billed usage.
- Preserve raw usage extensions. Current Responses `readUsage` keeps tokens and then omits original `usage` from `native`, which would lose reported cost, BYOK and tool accounting. Keep provider-reported cost separate from our catalog estimate; include no server-tool fees in the estimate. Route-dependent rates/TTL and server loops can make an estimate incomplete.
- Record resolved response model and upstream provenance. Current assistant construction records requested `request.model`; aliases/router models can therefore mislabel replay provenance. Preserve the requested value separately, and test how the selected slug is reported.
- Messages reuse also needs router errors/usage, Bearer auth/beta-header handling, and provider-specific reasoning replay. Its present generic cross-model rule strips `thinking/redacted_thinking`; that can delete router deferred state. Do not apply the direct-Anthropic exception unchanged to OpenRouter.

These observations come from the current local Responses/Messages adapter files and the sources above; **no implementation files were changed**. OpenRouter conflicts with our no-silent-loss principle at several upstream boundaries. A truthful profile promises verbatim behavior at our boundary and refuses known unsafe requests; it cannot make unverified router translation lossless. Keep explicit conversion helpers for model/format changes and report loss.
